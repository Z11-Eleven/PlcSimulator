# 潜江太蓝 PLC 模拟器（Modbus TCP 服务端）

从 WCS 源码逆向出的 PLC 模拟器。没有真实 PLC、或 PLC 被产线占用时，用它替代，
让 WCS 能连上并端到端跑通业务流程，也可作为长期回归测试工具。

## 快速开始

```bash
dotnet build PlcSimulator/PlcSimulator.slnx
```

```bash
dotnet test PlcSimulator/PlcSimulator.slnx
```

校验配置（不启动服务，只检查点位、地址重叠、监听地址等）：

```bash
dotnet run --project PlcSimulator/PlcSimulator.Cli -- check PlcSimulator/config/simulator.json
```

启动模拟器：

```bash
dotnet run --project PlcSimulator/PlcSimulator.Cli -- serve --config PlcSimulator/config/simulator.json
```

加 `--log-frames` 可实时打印收发的报文。

## 从数据库生成配置

点位变动时不用手工对齐地址，导出数据后用导入工具重新生成即可。
命令行与调试台的「配置生成」页共用同一套解析与生成代码，两种用法等价。

**1. 导出数据**：查询 `wcs_opcitem`（例如 `select * from wcs_opcitem where groupname='Convery'`），
导出的 **`.xlsx` 工作簿直接可用**（读第一个工作表）；CSV 也行，Excel 另存为 CSV 即可。

**2. 生成配置**

```bash
dotnet run --project PlcSimulator.Import -- 导出文件.xlsx -o config/simulator.production.json
```

| 选项 | 说明 |
|---|---|
| `--ip <IP>` | 覆盖设备 IP（默认用数据库 `userid` 字段） |
| `--port <端口>` | 设备端口，默认 502 |
| `--protocol-type <协议>` | 对接协议（决定各字段的字节偏移），默认 NTI |
| `--value-is-byte` | 把 `value`/`signaltype` 当字节解释；**默认按寄存器**（字节偏移 = value × 2） |
| `--delay` / `--jitter` | 模拟动作延时与抖动，默认 3000 / 200 |

同样的参数在调试台的「配置生成」页上都有，生成完可以直接加载，见下文。

**3. 校验**

```bash
dotnet run --project PlcSimulator.Cli -- check config/simulator.production.json
```

会打印每个站台的字节偏移与寄存器地址，可与 WCS 实际发出的读地址对照。

**分组规则与 WCS 一致**（`ConveryPLC.ConveryInit`）：IP + DBAddress + belong + field1 四项相同即同一组；
`belong=0` 的行跳过（WCS 不仿真这些站台）。

**数据修订记录（`stationNo` 重复，2026-09-25 已修复）**：早先的导出数据里有两个重复的 `stationNo`：

| stationNo | 位置 | 名称 | 身份 |
|---|---|---|---|
| `10022` | 字节偏移 120 与 1140 | "1002-1" 与 "1019-1" | 前者是 10021 的第二层（与它共用寄存器，合法）；后者是**另一台独立提升机**，占用了同一个站台号 |
| `10531` | 字节偏移 3180 与 3480 | "1053-1" 与 "1058-1" | 前者是另一台设备；后者才是与 `10582` 配对的那一层（共用偏移 3480） |

**后果（WCS 侧）**：`ConveryPLC.StationsInfo` 是用 `Find(...)` 按 `StationNo` 查的，只返回**第一个**匹配项，
因此第二个同号站台的寄存器段会被**永远丢弃**——地址占着，但那一段的数据不会被解析、也不参与业务。

**后果（模拟器侧）**：拓扑按 `stationNo` 建图、提升机按站台号前 4 位归组，这两处重复同样会让路线失真：

| 站台号 | 在图上表现为 |
|---|---|
| `10022` | 两行的**站台号**都含前缀 `1002`，被并进同一台提升机——`1019-1` 那台的邻居 `1018` 混了进来，凭空多出一条近路：`1001 → 1017` 会走成 `1001 → 10021 → 1018 → 1017`（3 跳），而不是沿主线的 5 跳 |
| `10531` / `10582` | `10531` 被两台设备共用，而 `10582` 与其中的 `1058-1` 才是同一台的两层——站台号前缀不同（`1053` / `1058`），图上**断成两个节点**：`1056 → 1017` 走不通，`1054`、`1059`、`1271` 等成了死路端 |

用调试台的「路径诊断」页对着这些站台号跑一次，能直接看到断在哪一站。

**修复（2026-09-25）**：重新导出的数据（`expdata_202609251702.csv`）已把重复的站台号拆开，
并让同一台提升机各层的前 4 位一致（`10021`/`10022`、`10531`/`10532`、`10581`/`10582`）。
`config/simulator.production.json` 已用新数据重新生成，
修订后 `1001 → 1017` 恢复为 5 跳、`1056 → 1017` 恢复通行。

> 这次修订同时说明了两条数据要求：**`stationNo` 不能重复**、**同一台提升机各层的站台号前 4 位必须一致**。
> 模拟器不做猜测，只如实反映建图结果，所以数据出问题时用「路径诊断」一眼能看出断在哪。

## 货物流转

模拟器不只是"抖心跳"，而是真的把货物在站台之间搬运：

```
WCS 写任务号 ─▶ 动作中（托盘在本站）
                  │ actionDelayMs
                  ▼
              下一站收得下吗？
                  ├─ 否 ─▶ 等下站（托盘仍留在本站，任务信息原样不动）
                  │         下一站一空出来就接着往下走
                  ▼ 是
              在途（托盘已离站，本站与下一站都无货）
                  │ transferDelayMs
                  ▼
              送达下一站（整份任务信息随货写入，下一站变有货）
                  │
                  │ 该站是 WCS 下的任务吗？
                  ├─ 是 ─▶ 待清零（置心跳） ── WCS 写清零值 ─▶ 空闲
                  └─ 否 ─▶ 空闲，货物继续往下一站走
```

要点：

- **先问下一站收不收得下，再发车**：下一站忙（或被打了手动）时托盘**留在本站**等，
  任务信息原样不动。托盘不会推到一半悬在路上——现场堵了就是停在某个站台上，
  等下游空出来再走
- **提升机不能停盘**：提升机（`remark = "提升机"`）是过路站，托盘不能在盘上停着。
  所以发给提升机前会**多看一站**——提升机的下一站收不下时，托盘留在**提升机的前一个站台**等，
  而不是先送进提升机再卡住
- **中间态可观察**：真正在途的那段时间起点与目标站台都是「无货」，界面上能看到这个窗口
- **在途中目标才变忙**：托盘已经在路上，只能在线上等待（由在途检查兜住）
- **整份任务信息随货移动**：任务号、货物类型、条码、目标站台一并写入目标站台，
  同时来源站台填成本站号码；**托盘离站时源站台清空**（这五项全归零），不留残余
- 搬过去的是「上一段的任务号」，只作随货标识，目标站台不会拿它当新任务再执行一次
- **任务号不做去重**：站台不记「我先前进过哪个号」。WCS 用同一个任务号再下一次就是新任务——
  托盘离站时本站字段已经清空，寄存器里 `0 → X` 的变化本身就是判据。
  只有站上停着等 WCS 处置的货时（送到终点站、或任务目标就是本站），
  随货带来的那个号才不被当成新任务，否则托盘一停稳就会被自己带来的号反复触发
- **目标不在仿真范围内**（虚拟站台等）：货物视为离场，本站直接完成

时间参数在站台的 `simulation` 里配：`actionDelayMs`（本站动作）、`transferDelayMs`（在途）。

## 逐站推进与拓扑

货物**不会从起点一步跳到终点**，而是按站台拓扑一站一站往前走，中间站台都会被真实占用
——这样下游堵住时，堵塞会自然向上游传导。

拓扑由模拟器按 WCS 的规则自行推导（`StationTopology`，规则移植自 `FindPathBLL.BuildAdjacencyTable`）：

- 同 `zonecode` 内，沿 `arrowdirection` 方向正好相邻的站台即为下一站
  （1 上 / 2 下 / 3 左 / 4 右，判定用邻站的宽高做偏移）
- **提升机**（`remark = "提升机"`）按 **站台号前 4 位**归组，整组塌缩成一个节点
  ——同一台设备的两层站台号形如 `10021` / `10022`，前缀 `1002` 即归组依据
- `arrowdirection = "0"` 或 `field5 = "1"` 的站台不参与拓扑
- 没有拓扑或找不到路径时，退回按任务里的目标站台**直接投送**（老行为）

**心跳只在 WCS 下发任务的站台产生**：中间站台只是把货往下传，转发完就回到空闲、不置心跳，
与现场「PLC 执行完 WCS 的任务后回执」的分工一致。

查看货物会走哪条路：

```bash
dotnet run --project PlcSimulator.Cli -- path PlcSimulator/config/simulator.production.json 1001 1017
```

```
1001 → 1017 共 5 跳：
  1001 → 10021 → 1004 → 1010 → 1015 → 1017

  1001 的出边：10021
  10021 的出边：1004
  ...
```

加 `--detail` 会把推导过程摊开——逐跳列出候选邻居与淘汰原因（这条走了、那条到不了目标），
按各站 `actionDelayMs` / `transferDelayMs` 推算的到达时刻，走不通时断在哪一站，
以及**方向对照**：把 `arrowdirection` 放开成四向皆可、用同一套算法再跑一遍，
沿那条路线逐跳检查原规则通不通——断在哪一跳、该给哪个站台补哪个方向值，直接写出来：

```
方向对照  同一张图、把 arrowdirection 放开成四向皆可
  放开方向后的路线：1001 → 10021 → 1004 → 1010 → 1015 → 1017
  这条路线要补 1 处方向（按断点最少选取，不是跳数最少）
  逐跳对照：
    ✓ 1001 → 10021
    ✓ 10021 → 1004
    ✗ 1004 → 1010   ← 第一处断裂
        1010 位于 1004 的左方：1004 的 arrowdirection 需要包含 "3"（当前为 "2"）
        1004 配的 "2"（下）方向没有相邻站台，而 "1"（上）、"3"（左）、"4"（右）方向有邻居却没配
        —— 方向值可能写反或写错了
    ✓ 1010 → 1015
```

断点提示分两句：第一句说**该补什么**，第二句做**方向体检**——把"配了却没邻居的方向"与
"有邻居却没配的方向"对起来，直接点出写反/写错。第二句只在确实存在这种矛盾时才出现。

寻路用的是 0-1 BFS：**原规则下能走的边记 0、需要补方向的边记 1**，取总代价最小的路线——
所以它只会挑出"最接近原规则"的那条，而不是一条几何上更近、却与原路径毫无关系的路。

```bash
dotnet run --project PlcSimulator.Cli -- path PlcSimulator/config/simulator.production.json 1001 1017 --detail
```

```
第 1 跳  1001（异常口） → 10021（1002-1，提升机）
  向左 · 动作 3000 ms(±200) + 在途 1000 ms · 发车 t≈0.0 s → 到达 t≈4.0 s
  目标站台是提升机：发车前会先确认它的下一站收得下，收不下就留在本站等（不能在盘上停留）
  候选邻居：
    ✓ 10021  向左 · 选中，成为出边 · 本跳走它
```

调试台的「路径诊断」页是同一套代码，另多一项**沿途实时状态**：
标出路径上哪些站正在忙或被打了手动，据此推演托盘实际会停在哪一站。

> **实现上与 WCS 的差异**（有意为之）：节点键与提升机归组键都用 **`stationNo`**——
> `itemname` 允许重复、只用于显示，不能作判据。WCS 用 `itemname` 作节点键，
> 数据里有 33 行（全是提升机）两者不一致，导致 WCS 寻路时查不到键、退回把最终目标
> 当作下一站——这正是「货物一步到位、不经过中间站台」的原因。
>
> 由此对数据有两条要求：**站台号不能重复**，且**同一台提升机的两层站台号前 4 位必须相同**。
> 不满足时这两层在图上会断成两个节点，经过它的路线要么走不通、要么绕行——
> 模拟器如实反映，不做猜测（见下节「数据问题」）。
>
> 尚未实现：堆垛机取货口（`stationtype = 5`）与其放货站台的连接，需要 `equipment` 表的
> `stationpoint` / `equipmentnum`，不在当前点位导出范围内。

## 手动模式与人为堵塞

调试台的「流程状态机」页每个站台都有一个「打手动」按钮。打手动的站台会**冻结**：

- **上游的托盘进不来**：要送到本站的托盘停在上游站台上等着（不会被推上路），
  堵塞沿输送线逐级向上游传导
- **本站的托盘不动**：动作中 / 在途的托盘原地留着，不推进、不丢失
- **状态字 X9 置 0**：WCS 轮询就能看出本站已脱离自动（0 = 手动，1 = 自动）

「恢复自动」后从冻结处继续，且**冻结时长不计入动作延时**——冻了多久都要重新等满，
不会解冻瞬间跳完剩余动作。面板上该行会铺一层浅橙底色，一眼看出哪些站台被打了手动。

两个有意的边界：

- **「待清零」不冻结**：WCS 的清零写与心跳回执属于通信，手动挡的是机械动作。
  现场手动模式下 PLC 照样回执，模拟器照此实现，于是 WCS 看到的是「通信正常、货不动」。
- **「复位」会清掉手动**：复位即回到配置初值（含 `simulation.initial.auto`），手动状态不保留。

**典型堵塞场景**：给 1001 下发到 1017 的任务，托盘走到 1004 之后把 1010 打手动，
托盘就**停在 1004 上**（带着完整的任务信息），WCS 那边任务一直不完成；
把 1010 恢复自动，托盘接着经 1015 走到 1017——
用来检验 WCS 的超时、报警与重试。

## 硬约束

1. **WCS 把 Modbus 端口硬编码为 502、站号硬编码为 1**，所以同机模拟多台设备**不能靠端口区分**。
   办法是使用 `127.0.0.x` 段（Windows 默认把整个 `127.0.0.0/8` 当回环，免配置），
   每个设备一个 IP，数据库 `wcs_opcitem.userid` 指向对应地址。
   跨机部署时把 `server.listen` 改成 `0.0.0.0`，此时只能靠站号或单设备模式区分。
   **仅限测试网段**：Modbus 无认证、模拟器也没有访问控制，`0.0.0.0` 相当于把一个谁都能写的数据区
   摆到局域网上，切勿接进产线网。

2. **字节序逐调用点不同，绝不能写死**。同一个设备的不同方向、不同字段规则都可能不一样，
   全部通过 `byteOrder.policies` 配置。改动前先核对 `docs` 指向的源码行号。
   配置里 `swapFromByteOffset` 表示「从该字节起每 2 字节反序」，
   `extraPairUnswapRanges` 用于条码这类单独规则的字段。

3. **寄存器数据区里存的是线路表示**（真实 PLC 寄存器里的字节），
   字节序变换只发生在 `StationRuntime` 的字段读写上，协议层不做任何字节序处理。

## 与 WCS 联调

1. 改数据库：把 `wcs_opcitem.userid` 里对应站台的 IP 改成模拟器所在地址。
2. 启动模拟器（见上）。
3. 启动 WCS，界面上的 PLC 状态应变绿、不再报「物流线读取数据失败」。
4. 站台初始状态应与配置一致（空闲 / 自动 / 无故障）。
5. 在 WCS 上给站台下发任务，观察模拟器日志出现任务号写入，
   随后心跳置 1、WCS 回写清零值 `00 02`、心跳归零。

## 调试台（WinForms）

```bash
dotnet run --project PlcSimulator/PlcSimulator.App -- PlcSimulator/config/simulator.json
```

- **点位监视表**：逐字段显示每个站台的当前值，可直接改值（相当于代替 WCS 下发）。
  虚拟模式 + 只刷新被改动的行，全量导入上万点位也不会卡。
- **报文日志**：十六进制原始帧 + 解析摘要，支持导出 CSV。
- **流程状态机面板**：每个站台当前卡在哪一步、停留多久，并带「有货/清空」「打手动」「复位」按钮。
- **路径诊断**：填起点与目标站台号，输出完整推导过程——逐跳的候选邻居与淘汰原因、
  按配置推算的时间轴、沿途哪些站正忙/被手动、以及走不通时断在哪一环。只读，不下发任务；
  与命令行的 `path --detail` 共用同一套代码。
- **配置生成**：从 `wcs_opcitem` 的导出（`.xlsx` 或 CSV）直接生成配置（与命令行导入工具同一套代码）：
  选文件、填参数、点「生成配置」，提示信息回显在页内；生成完会问要不要立即加载。

**换配置文件**：工具栏「打开配置…」选一份 JSON 即可切换，会先校验、通过了才停掉当前服务
（选错文件不会把手上这份弄丢）；之前在运行的话自动重新启动。上次打开的路径会记住，
下次启动没给命令行参数时直接用它。

界面上点「启动」才会真正监听端口，**不要与命令行宿主同时启动**（两者都占 502 会冲突）。

> 线体布局图**不做**：站台位置、走向、载货状态在 WCS 界面上已经有了，模拟器再画一遍是重复的。
> 需要核对站台位置时看 WCS，需要核对模拟器内部状态时用「点位监视表」与「流程状态机面板」。

## 故障注入

用来验证 WCS 的容错行为。总开关 `faultInjection.enabled`，每条规则可单独启用，
也可以在调试台的「故障注入」页运行时勾选。被命中的报文会在「报文日志」里标注规则名。

| 效果 | 行为 | 可验证的 WCS 行为 |
|---|---|---|
| `SilentDrop` | 不回帧，让客户端自己超时 | 读失败后标红并降速到 5s 重连 |
| `CloseConnection` | 直接断开 TCP | 断线重连逻辑 |
| `ExceptionResponse` | 回指定异常码（2=非法地址、6=从站忙…） | 错误处理分支 |
| `DelayThenPass` | 延迟 N 毫秒后正常响应 | 超时判定边界 |
| `DelayThenException` | 延迟后回异常 | 组合场景 |
| `HeartbeatStop` | 语义级：站台动作完成但不置心跳 | 设备无响应时 WCS 是否卡死或报警 |

匹配条件支持设备、来源地址、连接角色（读/写）、功能码白名单、地址范围，
另有 `probability`（概率）与 `maxTimes`（最多命中次数）。

两个设计要点：

1. **故障门位于「解码之后、访问数据区之前」**，因此故障永远不会把寄存器状态改坏——
   被拒绝的写不会落盘。这一点有测试守着。
2. **默认是零分配的直通实现**（`PassThroughFaultInjector`），只在配置开启且确实有启用规则时
   才替换成会匹配的实现，未开启故障时不引入任何每请求开销。

## WCS 侧问题记录（四条均已由用户在 2026-09-23 修复）

模拟器按现场协议与 Modbus 标准搭好参照系后，暴露出下列四处 WCS 侧问题，
均由用户确认并在 WCS 中修复。**以下保留完整的现象与代码定位**，
便于日后核对、回归，或作为同类问题的排查参考。

### WebSocket 推送的载货状态与协议相反（2026-09-22 记录，2026-09-23 已修复）

**现场协议**：状态字 X8 StaLoad：**0 = 有货，1 = 无货**。

**数据流核对**：

| 环节 | 代码 | 是否正确 |
|---|---|---|
| PLC → checkinfo | `ConveryPLC.cs:408` `statusArr[8] == 1 ? 1 : 2` | ✓（1=无货，2=有货） |
| 桌面界面显示 | `FrmConveryManager.cs:1191` `checkinfo == "1" ? "空闲" : "载货"` | ✓ |
| **WebSocket 推送** | `CWCS.WebBridge/Common/BridgeWebSocketClient.cs:90` `checkinfo == 2 ? "unloaded" : "cargo"` | **✗ 相反** |

`checkinfo == 2` 是**有货**，却映射成 `"unloaded"`；`checkinfo == 1`（无货）映射成 `"cargo"`。
同一份数据，桌面端正确、Web 推送相反。

**影响**：通过 WebSocket 展示的载货状态全部相反。

**模拟器侧无需改动**：X8 编码已符合协议（`StationInitializer.ApplyStatus`），有测试固化。

### 状态字 Fault 位判定相反（2026-09-22 由用户提供协议确认，2026-09-23 已修复）

**现场协议**：设备状态是站台字节 28-29 组成的 16 位位域：

| 位 | 名称 | 含义 |
|---|---|---|
| X8 | StaLoad | **0 = 有货，1 = 无货** |
| X9 | AUTO | 1 = 自动，0 = 手动 |
| X10 | Fault | **1 = 有故障** |
| X11-X14 | CW / CCW / UP / DN | 正转 / 反转 / 上升 / 下降 |
| X0-X7、X15 | Element_9..16 / Element_8 | 备用 |

模拟器的默认初值为「无货 + 自动 + 无故障」，即状态字 **`0x0300`**（可逐站台在
`simulation.initial` 里配置 `loaded` / `auto` / `fault`）。

**WCS 的解析**（`ConveryPLC.cs:412-414`）：

| 位 | WCS 的判断 | 与现场定义 |
|---|---|---|
| X8 | `bit8 == 1 → 空闲`，否则"有货" | 语义一致（1 = 无货 ≈ 空闲） |
| X9 | `bit9 == 1 → 自动` | 一致 |
| X10 | `bit10 == 0 → faultflag = 1（有故障）` | **完全相反** |

**影响**：WCS 把"无故障"判成"有故障"、把"有故障"判成"正常"。
按现场定义正常待机状态字为 0，WCS 会把**所有正常站台都报成故障**。

**模拟器侧**：已按现场位定义实现（`StationInitializer.ApplyStatus` 与
`ConveyorStationMachine.UpdateStatusBits`），并有测试固化
（`StatusBits_DefaultStation_WritesZero`、`StatusBits_FaultBit_IsSetOnlyWhenFaulted`、
`StatusBits_AutoBit_FollowsAutoFlag`）。X11-X14 的动作方向本模拟器暂不产生。

### 单字段写缺少高低位转换（2026-09-21 定位，**2026-09-23 已由用户在 WCS 侧修复**）

**现象**：写入目标站台 `5555`（`0x15B3`），PLC 侧读到 `45845`（`0xB315`），正好是高
低字节互换。

**定位**：WCS 两条写路径对字节序的处理不一致。

| 路径 | 代码位置 | 对偏移 ≥ 6 的字节 |
|---|---|---|
| 整块写 | `ConveryPLC.cs:867-872` | **做**字交换 |
| 单字段写 | `ConveryPLC.cs:1003-1007` | **不做**（`ConvertHelper.GetHexBytes` 直转大端） |

NTI 协议实际只走单字段写（`ConveryPLC.cs:764-766`），所以整块写那套交换对它从不生效。

**受影响字段**（按 `WriteType` 的 index）：`ToStation`@6、`Heartbeat`@8、`Barcode`@12-27。
偏移 < 6 的 `TaskNum`@0、`GoodType`@2、`FromStation`@4 不受影响。

**特别注意**：心跳在 @8，同样缺转换。若 PLC 按交换约定存放，写 `2` 会变成 `0x0200`，
心跳握手会失效。

**修复状态（2026-09-23）**：用户已在 WCS 侧修改数据交换规则，写入不再需要高低位转换。
模拟器随之把解读口径从「整块写约定（偏移 ≥6 交换）」改回**单字段写口径（恒等，不交换）**
（`DeviceRuntime.IncomingPolicy`）。此前为了让缺陷显现，`to` 这类字段会被读成交换后的错值
（写 `1004` 读成 `60419`）；现在按普通值写即可正确路由。

**如果将来两个口径再次不一致**，点位监视表会把差异标出来：新增的「写入侧释义（状态机读到）」
列与「当前值（WCS 读到）」不同时会高亮。

### 站台数据解析偏移（2026-09-21 记录，2026-09-23 已修复）

**现象**：在标准 Modbus 语义下（站台数据位于寄存器 `value`、占 `signaltype` 个寄存器，
见 `config/simulator.production.json`），WCS 界面上的站台状态呈「正常／故障」**交替**出现。

**定位**：`CWCS.Core.Library/PLCManager/ConveryPLC.cs:371`

```csharp
byte[] bytetemp = new byte[si.length];
Array.Copy(byt, si.value - startValue, bytetemp, 0, si.length);
```

`Array.Copy` 的第二个参数是**字节下标**，而 `si.value - startValue` 是**寄存器差**
（`value` 已由线路地址证实是寄存器地址），少乘了 2。
结果 WCS 取数据的位置只有正确位置的一半，每隔一个站台错开一次。

**支撑证据**：WCS 发出的读地址范围是寄存器 `[30, 19260)`，与数据库 `value` 的范围
（30 → 19230）完全吻合，说明 `value` 确实是寄存器地址；而该范围在标准布局下正好覆盖
所有站台，WCS 却解析出交替状态。

**判定方法**：用 `config/simulator.production.json` 启动，观察 WCS 界面是否出现交替现象。

**修复状态（2026-09-23）**：用户确认此处并按标准语义修正，模拟器的
`config/simulator.production.json`（站台数据位于寄存器 `value`、占 `signaltype` 个寄存器）
即为正确基准。
