# PlcSimulator 代码评审报告（2026-09-25）

**评审基线**：非 git 仓库，本报告对应 2026-09-25 10:56 的文件快照（7 个源码项目 + 4 个测试项目，含测试共约 10.9k 行）；评审时 `dotnet build` 全绿（0 警告 0 错误）。
**评审范围**：全部生产代码（Protocol.Modbus / Core / Devices / Hosting / App / Cli / Import），测试工程未计入问题统计。
**评审维度**：边界条件、异常处理、性能瓶颈、安全分析。每条标注所属维度。
**本次评审未改动任何代码**，每条问题附最小修改方案。

## 高严重度

### H1.【异常】引擎循环无异常隔离，单个异常会静默冻死整个仿真

`SimulationEngine.cs:147` 的 `RunAsync` 只 catch `OperationCanceledException`。`ApplyPendingOperations` 里 GUI 排入的 `action()`（`SimulationEngine.cs:141`）或任一 `machine.Tick` 抛出异常，`_loop` 立即终结：站台全部定格、无任何日志；而 `StopAsync`（`SimulationEngine.cs:106`）同样只 catch OCE，异常会一直藏到停机那一刻才冒出来。对长期回归工具，"仿真冻死"会被误判成 WCS 卡死，正好摧毁这个工具的立身之本。

**最小方案**：`ApplyPendingOperations` 内对每个 action 加 `try/catch (Exception)` 记日志继续；`foreach machine.Tick` 同样逐台隔离，单台异常只冻结该台（置 Fault 态）并记日志，不带走整个循环。

### H2.【安全/边界】Windows 下 `SO_REUSEADDR` + `ExclusiveAddressUse=false` 允许端口双绑

`ModbusTcpServer.cs:72-73`。Windows 的 `SO_REUSEADDR` 语义等价于"允许别的进程绑同一地址"——第二个模拟器实例（或上次没退干净的残留进程）绑定同一 `127.0.0.x:502` **不会报任何错**，TCP 流量在两个进程间分摊。联调时表现为"改了配置/代码却不生效、报文时有时无"，极难排查。

**最小方案**：删掉这两行（默认即独占绑定），端口冲突时让 `listener.Start()` 直接抛 `SocketException` 报错。

## 中严重度

### M1.【异常】宿主日志回调跨线程直写 WinForms 控件；CLI 侧并发写非线程安全的 StreamWriter

`MainForm.cs:216` `_host.Log = message => _statusLabel.Text = message`，而 `Log` 由引擎线程触发（`SimulatorHost.cs:139` 的 `StationChanged` 转发）。这与类注释"后台线程从不触碰控件"（`MainForm.cs:13`）直接矛盾；全工程无任何 `BeginInvoke`/跨线程封送（已 grep 确认）。.NET 10 下 `CheckForIllegalCrossThreadCalls` 默认关闭，不会抛异常但属于未定义行为。
CLI 侧同一模式：`PlcSimulator.Cli/Program.cs:117` 的 `EntryAdded` 在**多个连接线程**上并发调 `WriteLine` → `StreamWriter.WriteLine`（`Program.cs:108-112`），StreamWriter 非线程安全，日志文件可能交错/损坏。

**最小方案**：GUI 侧把 `Log` 回调改为 `BeginInvoke`（或 `SynchronizationContext.Post`）封送；CLI 侧在 `WriteLine` 内对 `logWriter` 加锁。

### M2.【异常】连接任务无兜底 catch 且不纳入停机等待

`ModbusTcpServer.cs:235-250` 只 catch 四类预期异常；寄存器层/故障注入器一旦抛出意外异常（如 NRE），连接任务静默终结、无任何日志，且任务是 `_ = Task.Run` 发射后不管（`ModbusTcpServer.cs:164`），异常永远无人观察。`StopAsync`（`ModbusTcpServer.cs:115`）只等 accept 循环，不等在途连接任务。

**最小方案**：`HandleConnectionAsync` 末尾加 `catch (Exception ex)` 走 `LogControl` 记"连接异常：{ex.Message}"后关闭连接。（停机等待可不补——连接任务都被取消令牌驱动，会自行收尾。）

### M3.【边界】CATL 中转路径读写布局混用，中继货物必丢

`ReceiveCargo` → `AcceptCargo`（`DeviceRuntime.cs:200-212`）把 `to` 写进**读布局**（CATL 为 @36）；而 `TryAutoForward`（`ConveyorStationMachine.cs:316`）用 `ReadIncomingU16("to")` 读**写布局**（CATL 为 @4），读到 0 → `HasTarget` 为 false → "目标不在仿真范围，货物离场"，货物凭空消失。NTI 因读写偏移恰好相同才不出事——这条正确性是巧合不是设计。根因是 `ReceiveCargo` 拿到了 `toStationNo` 参数却丢弃，下一 tick 靠回读寄存器还原目标。另 `goodstype` 在 CATL 读布局是 U8@7，`AcceptCargo` 却按 U16 写 2 字节，会踩到相邻字节。

**最小方案**：`ReceiveCargo` 把 `toStationNo` 存进 `_cargoFinalTargetNo`，`TryAutoForward` 用它而不是回读寄存器。（CATL 一期未实测，属潜伏 bug，建议实测前先修。）

### M4.【异常】GB2312 回退是死代码，乱码会静默传导成错误拓扑

`ImportTable.cs:57-68`：`Encoding.UTF8` 默认是替换容错，**永远不会抛 `DecoderFallbackException`**，catch 分支不可达。无 BOM 的 GB2312 导出会被按 UTF-8 读成乱码：`stationno` 等 ASCII 列幸存所以配置照常生成，但 `remark`/`zonecode` 中文列全乱 → `StationTopology.cs:67` 的 `Remark == "提升机"` 归组静默失效 → 提升机不走分组塌缩，货物路径与 WCS 不一致，且全程无提示。

**最小方案**：`File.ReadAllText(path, new UTF8Encoding(encoderShouldEmitUTF8Identifier: false, throwOnInvalidBytes: true))`，让 catch 真正生效。

### M5.【安全/边界】无空闲超时 + 每 IP 仅 8 连接，配额可被僵尸连接占满

`MaxConnectionsPerIp=8`（`ModbusTcpServer.cs:17`），但连接无任何读超时（`ModbusTcpServer.cs:192` 的 `ReadExactlyAsync` 无限等）。WCS 的闭源 DLL 若卡住不关闭旧 socket，8 条僵尸连接占满配额后，WCS 的重连会被"接受后立即关闭"（`ModbusTcpServer.cs:155-161`），表象是模拟器不服务了。

**最小方案**：给每条连接挂一个空闲超时（如 5 分钟无帧则关闭），或至少把"因超限拒绝连接"写一条控制日志（当前这条路径无日志，`ModbusTcpServer.cs:158` 直接 Dispose）。

## 低严重度

### L1.【边界】FC23 未计入 `IsWrite`

`ModbusRequest.cs:17-21` 漏了 `ReadWriteMultipleRegisters`（它含写操作）。首帧为 FC23 的连接被判成读角色，`Role=W` 的故障规则对其失效。
**最小方案**：模式匹配里补上该功能码。

### L2.【边界】FC15 写多线圈部分应用 + 位写非原子

`ModbusRequestProcessor.cs:205-212` 逐位写入，中途越界时前面的位已落寄存器却回异常响应（真实设备整批校验后拒绝）；`WriteBit`（`:218-230`）的读-改-写跨两条连接非原子，相邻位并发写会丢更新。WCS 实际不用线圈功能码，故定低。
**最小方案**：先全量校验地址范围再落写；位操作下沉为 `DeviceRegisterSpace` 内在 `_sync` 下完成的方法。

### L3.【边界】读路径永不报 IllegalDataAddress

`DeviceRegisterSpace.cs:75-84` 块外读恒零填充，`TryReadRegisters` 对参数合法的范围恒返回 true。WCS 读错地址拿到全 0 无任何信号，与写路径的 0x02+详细日志（`ModbusTcpServer.cs:412-426`）不对称。注释表明这是有意取舍（稀疏块填零），但建议至少在报文日志对"完全落在块外的读"打一条提示。不改也能接受。

### L4.【边界】运行中关窗要按两次 X

`MainForm.cs:86-98`：`e.Cancel = true` 后 await 停机，但没有再次 `Close()`，首次关闭被永久取消，窗口留着。
**最小方案**：`_host = null` 后加一行 `Close()`（或 `BeginInvoke(Close)`）。

### L5.【边界】工具栏"复位全部站台"绕过引擎线程且不复位状态机

`MainForm.cs:114` → `SimulatorHost.cs:116` 直接在 UI 线程逐字段写寄存器（与同一时刻的 tick 并发，多字段复位非原子），且状态机的在途货物、`_lastCompletedTaskNum` 等内存状态全部保留——与单站"复位"（Enqueue + `machine.Reset`，寄存器+状态一起复原）语义不一致。
**最小方案**：改为对每个 machine `Engine.Enqueue(m.Reset)`。

### L6.【性能】`DirtyRangeTracker` 在无 GUI 消费时无界增长

`Mark`（`DirtyRangeTracker.cs:19-23`）每次写入追加，`TakeMerged` 只有点位监视表调用。CLI 模式跑长期回归（本项目的既定用途）时每天累计十万级条目，缓慢胀内存。
**最小方案**：`_ranges` 超过阈值（如 4096）时在 `Mark` 内就地合并，或加"无消费者即丢弃"开关。

### L7.【边界】字节序配置面大于实现，存在静默失灵的旋钮

`DeviceRuntime.WritePolicy`（`DeviceRuntime.cs:53`）全工程无人读取；`ByteOrderPolicy.Transform/EncodeForWire/DecodeFromWire`（`ByteOrderPolicy.cs:57-89`）只有测试调用；`ApplyOn` 解析后无人消费。配置里的 `"NTI-ConveyorWrite"` 和 `"applyOn"` 改了对运行行为**零影响**。字节序是这个项目文档化的"最大的坑"，失灵的旋钮比没有旋钮更危险（改了以为生效）。
另外 `StationInitializer.cs:7` 注释说数据区存"内部表示"，与 `DeviceRuntime.cs:86` 的"线路表示"直接矛盾，必有一个是错的（实际是线路表示）。
**最小方案**：删掉 `WritePolicy`/`ApplyOn` 或接上实际路径，二选一；修正注释。

### L8.【异常】配置校验缺口三处

①不查重复 listen 端点（同 ip:port 两条 → 运行期才 SocketException）；②不查同端点重复 SlaveId（`StaticDeviceResolver.Find` 静默返回第一台，第二台永远不可达）；③`protocolTypeRaw` 显式写 `null` 时 `ConfigLoader.cs:76` `.Contains` 抛 NRE。另 CLI 三个命令对 `LoadFromFile` 的 IO/JSON 异常无兜底（`PlcSimulator.Cli/Program.cs:77` 等），GUI 有而 CLI 没有。
**最小方案**：Validate 里加重复端点/站号检查，`ProtocolTypeRaw.Contains` 前判空；CLI 顶层包一层 try/catch 输出干净错误。

### L9.【边界】故障规则按名字运行时开关

`ConfiguredFaultInjector.cs:64-76` 按名字找到第一条即返回；多条未命名规则在 GUI 上全显示"(未命名规则)"，勾选只切第一条。另 `SuppressHeartbeat`（`:61`）忽略 `deviceId`，跨产线同站台号会被一起抑制。
**最小方案**：GUI 按行索引而不是名字回调。

### L10.【异常】无效 `effect` 字符串静默落到 `ExceptionResponse`

`ConfiguredFaultInjector.cs:81-84`。配置拼错（如 `Silentdrop`）无任何提示就变了语义。
**最小方案**：解析失败时在配置校验阶段报错或至少告警。

### L11.【边界】报文导出 CSV 无 BOM

`FrameLogView.cs:138` 用 `Encoding.UTF8`（.NET 下无 BOM），Excel 打开中文摘要列乱码——与工程记忆里 PS 5.1 ANSI 坑同源。
**最小方案**：`new UTF8Encoding(true)`。

## 四维度总评

- **边界条件**：主要缺口集中在"功能码边角"（FC15/FC23）与 CATL 未实测路径；NTI 主闭环（下发→执行→在途→送达→心跳→清零）逐行走查未发现偏差，心跳握手、堵塞传导、手动冻结的边界处理是扎实的。
- **异常处理**：最弱的一维。H1/M1/M2 同属一类病根——后台线程的异常与日志没有统一出口，静默失败随处可见；GUI 侧反而包得很细（配置加载、导入、写值都有兜底弹框）。
- **性能瓶颈**：架构选择正确（50ms 单线程 tick、环形缓冲、虚拟列表、脏区增量刷新），无热点瓶颈；唯一实质问题是 L6 的无界增长。环形缓冲 200k×原始帧上限约 50MB，有界可接受。
- **安全分析**：默认配置绑 `127.0.0.1`、xlsx 解析不解包落盘（无 zip-slip）、XmlReader 默认禁 DTD（无 XXE）、连接计数正确，这些都对。攻击面集中在两点：H2 的端口双绑，以及配置注释里提供的 `0.0.0.0` 跨机选项——一旦启用，这是一个无认证可写的 Modbus 服务暴露在局域网（Modbus 本身无认证，模拟器也未加 ACL），建议在配置注释里补一句"仅限测试网段，勿暴露到产线网"。

2. **M3 在 CATL 实测前修**；**M4 在下次导入真实导出文件前修**。
