# WCS 侧检验清单

用模拟器作为参照系，逐项核对 WCS 的 Modbus 行为是否符合现场协议。
每项都给出**可直接执行的命令**和**真实预期输出**，照着做就能出结论。

## 准备

```bash
dotnet run --project PlcSimulator/PlcSimulator.Cli -- serve --config PlcSimulator/config/simulator.production.json --log-file PlcSimulator/logs/verify.log
```

- `--log-file` 会把报文与状态机流转即时落盘，便于留证
- 加 `--log-frames` 可同时在控制台看到

**前置检查**：

- 确认 502 端口上跑的是你要测的那个实例（多个模拟器会互抢端口，症状是数据"莫名其妙"）
- 模拟器的默认状态：`status = 768`（`0x0300` = X8 无货 + X9 自动 + X10 无故障），`tasknum = 0`，`heartbeat = 0`

---

## 检验 1：状态字编码是否符合现场协议

**目的**：确认模拟器写出的状态字与协议一致，作为后续判读的基准。

**操作**：读站台 1001 的状态字（寄存器 44 = 字节 88 = 站台起点 60 + 状态偏移 28）

```python
import socket, struct
def req(tid, addr, qty=1):
    s = socket.create_connection(("127.0.0.1", 502), timeout=5)
    s.sendall(struct.pack(">HHHB", tid, 0, 6, 1) + struct.pack(">BHH", 3, addr, qty))
    r = s.recv(512); s.close()
    return struct.unpack(f">{qty}H", r[-2*qty:])

print("tasknum  =", req(1, 30)[0])   # 期望 0
print("heartbeat=", req(2, 34)[0])   # 期望 0
print("status   =", req(3, 44)[0])   # 期望 768 = 0x0300
```

**预期输出**
```
tasknum  = 0
heartbeat= 0
status   = 768
```

**判读**：`768` = `0b011_0000_0000` → X8=1（无货）、X9=1（自动）、X10=0（无故障）。
与协议表一致即为通过。若 X8/X9 对不上，说明状态字编码有问题。

## 检验 2：任务下发与心跳闭环（核心）

**目的**：验证"下发任务 → 设备动作 → 置心跳 → WCS 清零"整条闭环。

**操作**：写任务号触发状态机，等心跳置位后读回；然后按 WCS 目前的行为写清零值。

```python
import socket, struct, time
def req(tid, pdu):
    s = socket.create_connection(("127.0.0.1", 502), timeout=5)
    s.sendall(struct.pack(">HHHB", tid, 0, len(pdu)+1, 1) + pdu)
    r = s.recv(512); s.close(); return r
def read(tid, addr):
    return struct.unpack(">H", req(tid, struct.pack(">BHH", 3, addr, 1))[-2:])[0]

# 1) 下发任务号 1001 到站台 1001（寄存器 30）
req(1, struct.pack(">BHH", 6, 30, 1001))

# 2) 等状态机动作完成
for i in range(8):
    time.sleep(1)
    print(f"+{i+1}s heartbeat = {read(10+i, 34)}")

# 3) 按 WCS 目前的单字段写方式写清零值 2（不做高低位转换）
req(20, struct.pack(">BHH", 6, 34, 2))
time.sleep(1)
print("清零后再读 heartbeat =", read(21, 34))
```

**真实预期输出**（在模拟器日志里，`--log-file` 指定的文件中）

```
→ FC=0x06 addr=30 qty=1 → 1001.tasknum payload=[03 E9] 值=1001
[1001] 动作中 - 收到任务号 1001，动作中（3053 ms）
[1001] 待清零 - 动作完成，心跳已置 1，等待 WCS 清零
→ FC=0x06 addr=34 qty=1 → 1001.heartbeat payload=[00 02] 值=2｜该字段约定需高低位转换，交换后=512
[1001] 待清零 - 等待 WCS 清零超时
```

**判读**（WCS 修复后）：

| 观察点 | 说明 |
|---|---|
| 能走到「动作中」 | 任务号写入被正确识别 |
| 3 秒后「待清零」、心跳 = 1 | 模拟器动作正常 |
| WCS 写清零值后站台**回到空闲** | 握手完成 ✓ |

> 修复前（2026-09-23 之前）这里会卡在「待清零」并在 10 秒后报超时：
> WCS 单字段写漏了高低位转换，写下去的 `2` 被 PLC 读成 `0x0200`。
> 详见 `WCS缺陷反馈.md` 问题 1。

## 检验 3：写路径的字段级检查

**目的**：确定缺陷的边界——哪些字段受影响、哪些不受影响。

**操作**：在 WCS 上真实下发一次任务，观察写请求序列。

**预期输出**

| 字段 | 偏移 | 预期 |
|---|---|---|
| `tasknum` | 0 | 值正确 |
| `goodstype` | 2 | 值正确 |
| `from` | 4 | 值正确 |
| `to` | 6 | 值正确（修复前会被读成交换后的错值，如 `1004` → `60419`） |
| `heartbeat` | 8 | 值正确 |
| `barcode` | 12 | 值正确 |

**判读**：各字段都能解出正确值即为通过。
出现任何字段值不对，说明两边的字节序口径又不一致了——点位监视表的
「写入侧释义」列会把这种差异高亮出来。

## 检验 4：轮询稳定性

**目的**：确认长时间运行不出问题。

**操作**：让 WCS 连续运行 10 分钟以上，不进行操作。

**检查项**

- 日志里是否一直是 `响应 PDU 242 字节`（无异常码 `0x02`/`0x03`）
- 有无连接断开重连记录
- 模拟器进程内存是否稳定（任务管理器观察）
- 日志里 `→ FC=0x03 addr=... qty=120` 的序列是否连续（435 个站台会被分成约 161 片，每轮完整覆盖 `[30, 19260)`）

**判读**：出现异常码或断连，记录当时的地址与数量再看。

---

## 检验 5：容错行为

**目的**：验证 WCS 在设备异常时的反应。

**操作**：在调试台「故障注入」页勾选对应规则，观察 WCS 表现。

| 规则 | 预期 WCS 行为 |
|---|---|
| `读不响应（验证 WCS 降速重连）` | 读失败 → 界面标红 → 轮询降到约 5 秒周期重连 |
| `立即断开连接` | 触发重连，恢复后继续轮询 |
| `非法地址` | 记录异常码处理分支 |
| `1004 心跳停止` | 设备不再置心跳，观察 WCS 是否会卡死或报警 |

取消勾选后应自动恢复正常。
