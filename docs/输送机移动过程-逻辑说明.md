# 输送机移动过程的模拟逻辑

说明模拟器怎样把 WCS 下发的任务"跑"成一次真实的托盘搬运：谁在哪一步介入、
托盘停在什么位置、任务信息什么时候跟着走、WCS 在寄存器里看得到什么。

文中的行号指向代码位置，链接均可点击。整体行为另有测试固化，
见 `tests/PlcSimulator.Devices.Tests/`（`CargoTransferTests`、`HopByHopTransferTests`、`ManualModeTests`）。

---

## 一、分层：谁在哪一步介入

| 层 | 线程 | 干什么 |
|---|---|---|
| 协议层 `ModbusTcpServer` | 每连接一个 Task | 收发 Modbus 帧，只读写数据区（锁内），**不碰业务** |
| 数据区 `DeviceRegisterSpace` | 上面的锁 | 存放「线路表示」的字节，与真实 PLC 寄存器等价 |
| 引擎 `SimulationEngine` | 单独一个线程 | 50 ms 固定 tick，逐台调用状态机 `Tick` |
| 状态机 `ConveyorStationMachine` | 引擎线程 | 全部业务逻辑：识任务、走货、置心跳、看下游 |

业务不跑在协议线程上，所以一个站台"思考"的时候不会卡住 WCS 的轮询；
反过来说，WCS 写进来的值要先落到数据区，状态机在**下一个 tick** 才能看见。

GUI 的按钮也不直接调状态机，而是 `Engine.Enqueue(...)` 排进引擎队列
（[SimulationEngine.cs:59](../PlcSimulator.Devices/SimulationEngine.cs#L59)），
避免界面线程和在途推进撞车——例如点「复位」的同时货正在在途，复位清掉了目标站台，
在途推进就会拿到空目标并抛异常，把整个仿真循环打断。

## 二、七个状态

定义在 [StationState.cs](../PlcSimulator.Devices/Stations/StationState.cs)：

```
Idle(空闲)  Loaded(有货待命)  Executing(动作中)  WaitingDownstream(等下站)
Transferring(在途)  Done(待清零)  Fault(故障)
```

一次完整的搬运：

```
          WCS 写任务号 tasknum
Idle/Loaded ─────────────────────▶ Executing          货物在站上，状态字 X8 = 有货
                                      │  有效动作时间 ≥ actionDelayMs + 抖动
                                      ▼
                            下一站收得下吗？（发车前检查）
                    ┌─────────────────┼──────────────────┬───────────────────┐
                    │ 收不下           │ 收得下            │ 目标就是本站         │ 无目标/不在范围
                    ▼                 ▼                  ▼                   ▼
            WaitingDownstream   Transferring       CompleteWithoutDelivery   同右：清字段
            托盘留在原地等       本站与下一站都无货    货物留站(_cargoStays)    货物视为离场
                    │ 下游空出来      │ 在途 ≥ transferDelayMs                      │
                    └──────▶ 发车     ▼                                          │
                              下一站 ReceiveCargo（整份任务信息随货写入）           │
                                      │                                          │
                      ┌───────────────┴───────────────┐                          │
                      │ 下一站是「中转」                │ 本站是 WCS 下的任务        │
                      ▼                               ▼                          ▼
                 下一站继续往下走                    写心跳 → Done ──WCS 写清零值──▶ Idle
                 本站回 Idle，不置心跳
```

## 三、一次搬运的逐步细节

### 1. 接单

[ConveyorStationMachine.cs:308](../PlcSimulator.Devices/Stations/ConveyorStationMachine.cs#L308)

只有在 `Idle` / `Loaded` 且不是中转货时才看寄存器：`tasknum` 非 0 就算新任务，
**不做「是否重复」的判断**——站台不记「执行过哪个号」，WCS 用同一个号再下一次仍是新任务
（托盘离站时本站字段已清空，`0 → X` 的变化本身就是判据）。
唯一的例外是站上停着等 WCS 处置的货：随货带来的那个号不算新任务，
否则托盘一停稳就会被自己带来的号反复触发。
接单时把 `actionDelayMs + NextJitter()` 采样一次存进 `_actionDelayMs`，
**抖动是每个任务一次，不是每 tick 变**。

### 2. 动作

[ConveyorStationMachine.cs:164](../PlcSimulator.Devices/Stations/ConveyorStationMachine.cs#L164)

`Executing` 期间货物**仍在站上**，状态字 X8 保持"有货"。
计时用 `EffectiveElapsedMs = 停留时间 − 手动冻结时长`，所以被手动冻了多久，解冻后都要重新等满。

### 3. 发车前的三项判定

[ConveyorStationMachine.cs:351](../PlcSimulator.Devices/Stations/ConveyorStationMachine.cs#L351)

动作时间到，先算下一站是谁（见第四节），然后：

- **目标是本站** → 不搬运，`_cargoStays = true`，走完成流程
- **目标不在仿真范围内**（虚拟站台、站台号写错）→ `ClearTaskFields()` 清掉寄存器，货物视为离场，本站直接完成
- **下一站收不下** → `WaitingDownstream`，**托盘留在原地，任务信息一个字节都不动**，每 tick 重试

### 4. 离站

[ConveyorStationMachine.cs:448](../PlcSimulator.Devices/Stations/ConveyorStationMachine.cs#L448)

真正发车这一刻 `ClearTaskFields()`——任务号、货物类型、来源、目标、条码五项全清，本站置无货。
此时起进入 `Transferring`，**起点和终点两个站台都是"无货"**，这个窗口在 WCS 界面上是能观察到的中间态。

### 5. 送达

[ConveyorStationMachine.cs:472](../PlcSimulator.Devices/Stations/ConveyorStationMachine.cs#L472)

在途时间满 `transferDelayMs` 后尝试投递：目标 `CanAcceptCargo` 才投，
否则**在线上等待**（这是第二种堵塞——发车前没堵，走到一半目标才变忙，只能在路上等）。
投递即调用 `target.ReceiveCargo(...)`，把任务号/条码/类型/来源/目标写进对方的寄存器
（按对方的**读**布局写，WCS 随后读到的是随货移动过的完整信息）。

### 6. 收尾

[ConveyorStationMachine.cs:505](../PlcSimulator.Devices/Stations/ConveyorStationMachine.cs#L505)

- 本站是**中转站**（货不是 WCS 发给它的）→ 回 `Idle`，**不置心跳**
- 本站是 **WCS 下任务的站** → 写心跳（NTI 写 16 位 `heartbeat`；CATL 写回执字节 `ack`）→ `Done`
- `Done` 里等 WCS 写清零值（NTI 是 `2`），读到就写回 0 并回 `Idle`；
  若本站是"货物留在本站"的那种，则回 `Loaded` 继续等下一个任务。
  等待超时（配置了 `clearTimeoutMs` 时）只发事件告警，**不改变状态**

### 7. 一个完整的例子：1001 → 1017

生产配置里一条真实的路线，全程 `arrowdirection = 3`（向左）、同属一个 `zonecode`：

| 站台 | x | 名称 | remark | 角色 |
|---|---|---|---|---|
| 1001 | 30 | 1001 | 异常口 | 任务起点 |
| 10021 | 29 | 1002-1 | **提升机** | 过路站（与另一层共用寄存器，图上塌缩成一个节点） |
| 1004 | 28 | 1004 | | 过路站 |
| 1010 | 27 | 1010 | | 过路站 |
| 1015 | 26 | 1015 | | 过路站 |
| 1017 | 25 | 1017 | 扫码 | 任务终点 |

每站 `actionDelayMs = 3000`、`transferDelayMs = 1000`、抖动 ±200 ms，于是每跳约 4 s：

```text
t(s)   0       4       8       12      16      20
       |       |       |       |       |       |
1001   ======>>
10021          ======>>
1004                   ======>>
1010                           ======>>
1015                                   ======>>
1017                                           V
```

`======` 是本站动作（3 s），`>>` 是在途（1 s），`V` 是到货。整条链 5 跳 ≈ 20 s，
再加 WCS 一个轮询周期读到心跳，约 21 s 走完。

三处值得对照代码看：

1. **第 1 跳发车前看了两站**。1001 的下一站是提升机 10021，而提升机不能停盘，
   所以 `TargetCanAccept` 实际检查的是**再下一站 1004** 收不收得下 —— 1004 忙的话，
   托盘留在 1001，根本不进提升机。
2. **每站各自计时**，没有一个全局的"运输时间"：1001 送达那一刻 10021 才开始动作，
   时间沿线路阶梯式累积；20 s 里有 15 s 是后面几站的动作时间。
3. **终点站不会被当成新任务**。1017 到货后下一 tick 就发现"目标即本站"，停在有货待命；
   随货带来的任务号已经记成"已完成"，不会被自己再执行一遍。
   WCS 读到的 `from` 是 **1015**（把货交给它的那一站），不是 1001。

## 四、路径怎么定的：逐站推进，不是一步到位

下一站由 `ResolveDestination`
（[ConveyorStationMachine.cs:458](../PlcSimulator.Devices/Stations/ConveyorStationMachine.cs#L458)）
决定，两条路：

1. **有拓扑** → `StationTopology.TryGetNextHop(本站, 最终目标)` 做 BFS 找最短路径，
   取路径的第 2 个点作为本次投送的下一站。**任务信息里带的是最终目标**，
   每个中间站都拿它重新寻路，所以托盘是一跳一跳走完全程的。
2. **无拓扑 / 找不到路径** → 退回任务里的目标站台，一步直达（老行为）。

拓扑本身
（[StationTopology.cs:45](../PlcSimulator.Devices/Topology/StationTopology.cs#L45)）
的规则：

- 同 `zonecode` 内，沿 `arrowdirection` 方向（1 上 / 2 下 / 3 左 / 4 右）**坐标正好相邻**的站台即下一站
- `arrowdirection = "0"` 或 `field5 = "1"` 的站台不参与拓扑
- **提升机按站台号前 4 位归组**（`10021` / `10022` 同属 `1002`），整组塌缩成一个节点——两层楼共用一段寄存器，在图上是一个点
- 节点键与归组键都用 `stationNo`：`itemname` 允许重复、只用于显示（WCS 用它作节点键，数据里有 33 行对不上，导致 WCS 查不到键而一步到位；模拟器有意纠正）
- 建图用**全部站台**（含别名站台），但状态机只按物理站台建——
  别名站台占着坐标位置，建图时丢掉它会把经过该位置的路径整条切断

查路线不用跑起来：

```bash
dotnet run --project PlcSimulator.Cli -- path PlcSimulator/config/simulator.production.json 1001 1017
```

## 五、两种"停"的区别

| | 什么时候 | 托盘在哪 | 任务信息 | 怎么恢复 |
|---|---|---|---|---|
| `WaitingDownstream` | 发车前发现下一站收不下 | **留在本站** | 原样不动 | 下游空出来就发车 |
| `Transferring` 里等待 | 已离站，途中目标变忙 | 概念上在**线上**，两站都无货 | 记在内存里 | 目标空出来就投递 |

设计意图：**托盘绝不会被推到一半悬在空中**。现场堵了就是停在某个站台上，
堵塞沿输送线逐级往上传导。

**提升机额外一条规矩**
（[CanPassThrough](../PlcSimulator.Devices/Stations/ConveyorStationMachine.cs#L417)）：
托盘不能在盘上停着。所以发给提升机之前会**多看一站**——提升机的下一站收不下时，
托盘留在**提升机的前一个站台**等，而不是先送进提升机再卡住。
普通站台 `CanPassThrough` 恒为 `true`，允许托盘停在自己这里。

"收得下"的判据是 `CanAcceptCargo = !IsBusy && !手动`，
其中 `IsBusy` 含 `Executing / WaitingDownstream / Transferring / Done`——
**`Done`（等 WCS 清零）也算忙**，这正是"上一个任务没被清零，下一个托盘就进不来"的堵塞来源。

## 六、随货信息为什么不全走寄存器

`ReceiveCargo` 把任务号/类型/条码/最终目标**同时记进内存**
（[ConveyorStationMachine.cs:263](../PlcSimulator.Devices/Stations/ConveyorStationMachine.cs#L263)），
后续不再回读寄存器。原因：寄存器那份按**读布局**写，回读走的是**写布局**——
CATL 下 `to` 在读布局 @36、写布局 @4，回读会把目标读成 0，货物就被当成"离场"丢掉。
只有 WCS 亲自下发的任务才以寄存器为准。

另外 `_cargoFromStationNo` 记的是**把货交给本站的那一站**（上一跳），逐站推进时一路更新，
所以 WCS 在终点读到 `from` 是倒数第二站，不是任务起点。
条码读的时候用 `ReadOutgoingAscii`、写的时候用 `WriteOutgoingAscii`——
同口径取出再写回，净交换 0 次，不会每站翻转一次。

## 七、心跳与状态字：WCS 眼中的模拟器

- **心跳只在"WCS 下发任务的站台"产生**。中间站台把货转发完直接回 `Idle`、不置心跳，
  与现场"PLC 执行完 WCS 的任务后回执"的分工一致。
- **状态字实时反映**
  （[UpdateStatusBits](../PlcSimulator.Devices/Stations/ConveyorStationMachine.cs#L615)）：
  - X8 StaLoad：只有 `Loaded / Executing / WaitingDownstream` 算"有货"；
    **在途与待清零都置"无货"**
  - X9 AUTO：`auto = !_manual`，打手动立刻变 0
  - X10 Fault：状态机进 `Fault`，或配置 `simulation.initial.fault` 直接指定
- CATL 走另一套单字节编码（`autoManual` / `status` / `fault`），且故障位是反逻辑。

## 八、手动模式如何插进来

`Tick` 的第一件事就是判手动
（[ConveyorStationMachine.cs:134](../PlcSimulator.Devices/Stations/ConveyorStationMachine.cs#L134)）：
手动则 `_frozenMs` 累加、直接返回，**状态本身不变**——动作中的还停在动作中，
在途的还停在在途，只是不再推进。效果是双向的：本站的托盘不动，
想送进来的托盘因为 `CanAcceptCargo == false` 停在上游等着。

唯一的例外是 `Done`：手动状态下**清零握手照常处理**，因为手动挡的是机械动作，不是通信。
现场手动模式下 PLC 照样回执，模拟器照此实现，于是 WCS 看到的是"通信正常、货不动"。

## 九、确定性

引擎用固定 50 ms tick 单线程驱动，所有时间推进都来自 `Tick(delta)` 的参数而不是
`DateTime.Now`，因此同一份配置 + 同一个随机种子（抖动）能完全重放。
测试用 `AdvanceOneTick()` 手工推进，
`ManualModeTests` / `HopByHopTransferTests` 就是这么逐跳断言货物位置的。

## 十、怎么查路线 / 怎么排错

两条入口，共用同一套诊断代码（`PathDiagnostics`）。诊断是**只读**的：
不下发任务、不碰数据区，随时可以反复查。

**命令行**：`path` 给结论，`--detail` 给过程。

```bash
dotnet run --project PlcSimulator.Cli -- path PlcSimulator/config/simulator.production.json 1001 1017 --detail
```

**调试台**：「路径诊断」页填起点与目标，比命令行多一项**沿途实时状态**——
标出路径上哪些站正在忙或被打了手动，据此推演托盘实际会停在哪一站。

报告分五段：结论与路线 → 全程耗时（按 tick 量化、含抖动区间）→ 逐跳的候选邻居与淘汰原因
→ 实时推演 → 方向对照。几种常见的"货不走预期路线"在这里能直接看出原因：

| 现象 | 报告里会指出 |
|---|---|
| 货物一步到位、不经过中间站 | 结论是"走不通"，并列出从起点可达、却到不了目标的站台——运行时找不到路径就退回按任务目标直接投送 |
| **某个站台的方向配错了** | 方向对照段：断在哪一跳、该站台需要补哪个方向值（见下） |
| 走了意料之外的近路 | 逐跳的候选邻居——多半是两台提升机被归成了同一节点，出边取了两层的并集 |
| 走到某站就不动了 | 实时推演段：下游站台忙或被打了手动，托盘留在哪一站等 |
| 站台号写了却查不到 | 结论"站台不在配置里"，或"不参与输送拓扑（`arrowdirection=0` / `field5=1`）" |
| 全程耗时和预期不符 | 时间轴段：按各站自己的 `actionDelayMs` / `transferDelayMs` 逐跳累加，能看出是哪一站参数配大了 |

**方向对照（排查断链用）**：把 `arrowdirection` 放开成四向皆可、用**同一套建图算法**再跑一遍，
沿这条路线逐跳检查原规则能不能走通：

```text
方向对照  同一张图、把 arrowdirection 放开成四向皆可
  放开方向后的路线：1001 → 10021 → 1004 → 1010 → 1015 → 1017
  这条路线要补 1 处方向（按断点最少选取，不是跳数最少）
  逐跳对照：
    ✓ 1001 → 10021
    ✓ 10021 → 1004
    ✗ 1004 → 1010   ← 第一处断裂
        1010 位于 1004 的左方：1004 的 arrowdirection 需要包含 "3"（当前为 "2"）
        1004 配的 "2"（下）方向没有相邻站台，而 "1"（上）、"3"（左）、"4"（右）方向有邻居却没配
        —— 方向值可能写反或写错了
    ✓ 1010 → 1015
```

断点提示分两句：第一句说**该补什么**；第二句做**方向体检**——把"配了却没邻居的方向"与
"有邻居却没配的方向"对起来，直接点出写反/写错（只在确实存在这种矛盾时才出现）。

这条路线是用 **0-1 BFS** 选的：放开方向的图上，**原规则下能走的边记 0、需要补方向的边记 1**，
取总代价最小的路线。所以它给出的总是"最接近原规则"的那条——
若直接取最短跳数，可能挑出一条几何上更近、却与原路径毫无关系的路，对比就失去意义了。

照着提示改数据库里的 `arrowdirection` 即可。若放开方向后**仍然**走不通，说明问题不在方向上
（多半是 `zonecode` 不一致或坐标没配齐），报告也会直接这么说。

> 这一对照之所以可信，是因为两张图出自**同一个** `StationTopology.Build`——
> 只是喂进去的 `arrowdirection` 不同。几何判定、zone 过滤、提升机归组全都是同一份代码，
> 不存在"诊断用一套规则、跑货用另一套"的偏差。
